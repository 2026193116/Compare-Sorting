# 정렬 비교 보고서 (셸 · 카운팅 · 칵테일 셰이커)

## 1. 과제 개요

본 과제는 세 개의 정렬 알고리즘을 하나의 공통 인터페이스로 구현하고, 입력 형태와 크기에 따라 비교 횟수·이동 횟수·실행 시간을 함께 측정하여 각 알고리즘의 특성을 비교하는 것을 목표로 한다.

- 비교 대상: 셸 정렬, 카운팅 정렬, 칵테일 셰이커 정렬
- 공통 가정: 오름차순 정렬, 동일한 입력 생성기, 동일한 측정 루틴, 동일한 출력 포맷
- 핵심 질문:
  - 어떤 입력에서 빠른가?
  - 어떤 입력에서 비교·교환이 많아지는가?
  - 안정성, 추가 메모리, 구현 난이도는 어떤 차이가 있는가?

이번 과제의 의미는 단순히 “정렬 함수가 잘 동작한다”를 넘어, 동일한 실험 환경에서 알고리즘이 어떻게 다른 동작 패턴을 보이는지 관찰하는 데 있다. 특히 알고리즘의 성능은 입력의 분포와 배열의 상태에 따라 크게 달라지므로, 정렬을 비교할 때는 단순히 한 번의 실행 결과만 보는 것이 아니라 다양한 입력 조건을 함께 고려해야 한다.

## 2. 구현 구조와 실험 인터페이스

### 2.1 전체 설계 의도

세 알고리즘을 각각 따로 구현하는 것만으로는 비교가 어렵다. 입력 생성 방식, 시간 측정 방식, 통계 집계 방식이 조금만 달라도 결과가 서로 다르게 보이기 때문이다. 따라서 모든 구현은 같은 인터페이스를 공유하도록 설계했다.

C 구현에서는 `SortFunction` 함수 포인터와 `SortStats` 구조체를 사용해 각 알고리즘을 공통 기준으로 호출한다. 함수가 받는 인자는 정렬 대상 배열, 배열 길이, 비교 함수, 통계 구조체이다. 이 설계를 통해 `main.c`는 알고리즘 이름을 직접 쓰지 않고도 각 정렬을 일관되게 실행할 수 있다.

```c
/* 개념적인 인터페이스 예시 */
typedef struct SortStats {
    long long comparisons;
    long long moves;
    double elapsed_ms;
} SortStats;

typedef void (*SortFunction)(int *arr, int n, SortStats *stats);
```

이 구조는 대부분의 정렬 실험에서 중요한 점을 보장한다.

1. 같은 입력 조건으로 모든 알고리즘을 시험한다.
2. 비교 횟수와 이동 횟수를 동일한 기준으로 기록한다.
3. 시간 측정이 구현마다 달라지지 않는다.
4. 알고리즘을 추가해도 측정 코드와 테스트 코드를 크게 바꾸지 않아도 된다.

### 2.5 입력 생성 방식

실험에서는 네 가지 입력 패턴을 사용한다.

- `random`: 무작위 배열
- `sorted`: 이미 정렬된 배열
- `reverse`: 역순 배열
- `duplicates`: 중복 값이 많은 배열

이 네 종류는 단일 정렬 알고리즘의 “좋은 경우/나쁜 경우”가 무엇인지 확인하는 데 매우 중요하다. 예를 들어 셸 정렬은 정렬된 배열에서 매우 빠르게 동작할 수 있고, 카운팅 정렬은 값의 범위가 비교적 제한적일 때 강점을 보인다. 반대로 카운팅 정렬은 값의 범위가 너무 넓으면 비효율적이 된다.

## 3. 알고리즘별 원리와 코드 설명

### 3.1 셸 정렬

셸 정렬은 삽입 정렬을 단일 배열 전체에 적용하는 대신, 일정한 간격(gap)을 두고 부분 배열을 정렬하면서 점점 간격을 줄여가는 방식이다. 이 구현에서는 초기 gap을 `floor(n/4)`로 정한 뒤, 매 pass마다 `gap = floor(gap/2)`로 줄이고 최종적으로 `gap = 1`에서 정렬을 마무리한다.

핵심 아이디어는 “큰 값이 멀리 떨어진 곳에 있으면 큰 간격으로 먼저 정리하고, 점점 세밀하게 다듬는다”는 점이다. 이 방식은 단순 삽입 정렬보다 더 많은 항목을 빠르게 자리 잡게 만들어, 큰 무작위 배열에서도 더 나은 성능을 기대할 수 있다.

#### 코드 관점의 설명

```c
for (gap = n / 4; gap > 0; gap /= 2) {
    for (i = gap; i < n; i++) {
        tmp = arr[i];
        j = i;
        while (j >= gap && arr[j - gap] > tmp) {
            arr[j] = arr[j - gap];
            j -= gap;
        }
        arr[j] = tmp;
    }
}
```

여기서 핵심은 `gap`을 통해 인접하지 않은 원소도 비교할 수 있다는 점이다. 예를 들어 배열의 원소들이 뒤섞여 있어도, 5칸 간격으로 떨어진 원소들이 먼저 정렬되면 이후 gap이 줄어들 때 짧은 거리의 오차를 빠르게 정리할 수 있다.

#### 장단점

- 장점
  - 추가 배열이 필요 없다.
  - 큰 규모의 배열에서 삽입 정렬보다 더 나은 성능을 보일 수 있다.
  - 구현이 비교적 단순하다.
- 단점
  - 안정 정렬이 아니다.
  - gap 수열에 따라 성능 편차가 크고, 최악의 경우 시간 복잡도가 높아질 수 있다.

#### 복잡도

- 추가 공간: `O(1)`
- 최선: `O(n log n)` (특정 gap 수열과 입력에 따라)
- 평균: 대체로 `O(n^1.5)` 수준으로 근사
- 최악: `O(n^2)`

이 구현에서는 시작 gap을 `n/4`로 고정했다는 점이 중요하다. 큰 값이 빠르게 정리되면서 전체 정렬 비용을 낮추는 방식으로 동작한다.

### 3.2 카운팅 정렬

카운팅 정렬은 값의 범위가 제한된 정수 배열에서 매우 강력한 알고리즘이다. 핵심은 각 값이 몇 번 등장하는지 개수를 세고, 그 누적 결과를 이용해 각 원소가 최종 배열에서 어디에 위치해야 하는지를 계산하는 것에 있다.

이 방식은 비교 기반 정렬이 아니라 “빈도 기반 정렬”에 가깝다. 따라서 정렬 대상 값이 작은 범위의 정수일 때, 비교 횟수보다 값의 등장 횟수 누적이 지배적인 방식으로 동작한다.

#### 코드 관점의 설명

```c
int max = findMax(arr, n);
int *count = calloc(max + 1, sizeof(int));

for (i = 0; i < n; i++) {
    count[arr[i]]++;
}

for (i = 1; i <= max; i++) {
    count[i] += count[i - 1];
}

for (i = n - 1; i >= 0; i--) {
    output[--count[arr[i]]] = arr[i];
}
```

이 과정에서 `count[x]`는 값 `x`보다 작거나 같은 원소가 총 몇 개인지를 의미한다. 이 누적 정보를 이용해 각 값이 어디에 배치되어야 하는지를 결정한다. 마지막으로 뒤에서부터 원소를 넣으면 중복 값이 있어도 안정성을 유지할 수 있게 된다.

#### 안정성

카운팅 정렬은 보통 안정 정렬로 분류된다. 같은 키를 가진 원소들의 상대적 순서를 보존할 수 있기 때문이다. 이는 정렬이 단순한 값 비교에 그치지 않고, “동일한 값끼리의 상대 위치”를 유지하는 데 중요하다.

#### 장단점

- 장점
  - 값의 범위가 작을 때 매우 빠르다.
  - `O(n+k)` 형태로 동작할 수 있어 대규모 데이터에 유리하다.
  - 안정 정렬이 가능하다.
- 단점
  - 정수 값 범위가 클 경우 메모리 사용량이 크게 늘어난다.
  - 일반적인 비교 기반 정렬처럼 실수나 문자열을 직접 정렬하기 어렵다.

#### 복잡도

- 추가 공간: `O(n+k)`
- 시간: `O(n+k)`
- 여기서 `k`는 입력값의 최대 범위를 의미한다.

값 범위가 제한된 경우에는 매우 우수한 성능을 보이지만, 값이 큰 범위에 걸쳐 분포되어 있으면 카운팅 정렬의 장점이 사라진다.

### 3.3 칵테일 셰이커 정렬

칵테일 셰이커 정렬은 버블 정렬의 변형이다. 한쪽 방향으로 큰 값을 뒤로 보내는 대신, 왼쪽에서 오른쪽으로 진행한 뒤 다시 오른쪽에서 왼쪽으로 진행하며 요소를 정렬한다. 버블 정렬이 한 방향으로만 교환을 수행하는 것과 달리, 칵테일 셰이커 정렬은 양방향으로 정렬 범위를 좁혀간다.

이 알고리즘은 특히 배열이 양 끝에서 이미 정렬된 상태에 가까울 때 유리할 수 있다. 그러나 전체적으로는 비교 횟수와 교환 횟수가 많아지기 쉬워, 무작위 입력에서 큰 장점을 내지 못하는 경우가 많다.

#### 코드 관점의 설명

```c
for (left = 0, right = n - 1; left < right; ) {
    swapped = 0;

    for (i = left; i < right; i++) {
        if (arr[i] > arr[i + 1]) {
            swap(arr[i], arr[i + 1]);
            swapped = 1;
        }
    }
    right--;

    for (i = right; i > left; i--) {
        if (arr[i - 1] > arr[i]) {
            swap(arr[i - 1], arr[i]);
            swapped = 1;
        }
    }
    left++;

    if (!swapped) break;
}
```

이 구조는 “한 바퀴를 왼쪽에서 오른쪽으로, 한 바퀴를 오른쪽에서 왼쪽으로” 진행한다는 점이 중요하다. 이것은 버블 정렬의 단일 방향 순회를 보완하는 형태다.

#### 장단점

- 장점
  - 구현이 단순하다.
  - 배열의 양쪽이 정렬 상태에 가까울 때 효율적일 수 있다.
  - 무작위 배열보다는 특정 분포에서 약간의 이점을 낼 수 있다.
- 단점
  - 여전히 `O(n²)` 수준의 비교를 수행한다.
  - 배열이 거의 정렬되어 있는 경우에도 비교를 피하지 못하는 구조다.

#### 복잡도

- 추가 공간: `O(1)`
- 최선: `O(n)` (교환이 거의 발생하지 않을 때)
- 평균/최악: `O(n²)`

칵테일 셰이커 정렬은 버블 정렬보다 약간 더 나은 경우가 있지만, 전체적으로는 큰 데이터에 대해서는 비효율적이다.

## 4. 코드에 대한 부가 설명

### 4.1 통계 누적의 중요성

정렬 알고리즘을 비교할 때 가장 중요한 것은 “어떤 기준으로 측정하느냐”이다. 본 프로젝트에서는 비교 횟수, 이동 횟수, 시간 측정을 모두 분리해 기록한다.

- 비교 횟수: 두 원소를 서로 비교한 횟수
- 이동 횟수: 원소가 한 칸 이동하거나 교환되는 횟수
- 실행 시간: 정렬 알고리즘 자체의 수행 시간

이 값들은 서로 다르게 변화한다. 예를 들어 버블 정렬은 비교 횟수는 비슷해도, 교환이 많아지면 이동 횟수가 급격히 증가한다. 반대로 카운팅 정렬은 대개 비교 횟수 자체가 적지만, 값의 범위에 따라 메모리 사용량이 커진다.

따라서 결과 분석에서는 “시간이 빠르다”만 보고 끝내지 않고, 무엇 때문에 빠른지까지 함께 설명해야 한다.

### 4.2 구현에서 가장 중요한 구조적 요소

#### 1) 반복문 구조

각 알고리즘은 모두 반복 구조를 통해 동작한다. 셸 정렬은 gap을 줄이는 반복문, 카운팅 정렬은 누적 배열 계산, 칵테일 셰이커 정렬은 좌우 양방향 순회로 구성된다. 이러한 구조는 곧 시간 복잡도와 입력 의존성을 결정한다.

#### 2) 배열 수정 방식

- 셸 정렬: 제자리 정렬, 추가 메모리 거의 없음
- 카운팅 정렬: 출력 배열을 별도로 사용
- 칵테일 셰이커: 제자리 교환 중심

즉, 구현 방식은 단순히 “정렬 결과를 맞춘다”를 넘어, 메모리 사용량과 성능 분포에도 직접적인 영향을 미친다.

#### 3) 안정성 판단 기준

동일한 키 값이 여러 개 있을 때 입력 순서가 보존되는지를 안정성으로 본다. 카운팅 정렬은 일반적으로 안정적이고, 셸 정렬은 불안정하다. 칵테일 셰이커 정렬도 기본적으로는 안정 정렬이지만, 구현 방식에 따라 안정성이 쉽게 깨질 수 있다.

## 5. 실험 방법과 시각화

### 5.1 실험 체계

본 실험은 다음 순서로 진행된다.

1. 입력 배열 생성
2. 동일한 입력을 각 알고리즘에 복사
3. 알고리즘 실행
4. 비교 횟수·이동 횟수·시간 측정
5. 정렬 결과 검증
6. CSV 저장 및 그래프 생성

이 과정은 모든 알고리즘에 동일하게 적용되므로, 결과를 공정하게 비교할 수 있다.

```mermaid
sequenceDiagram
    participant M as main.c
    participant G as 입력 생성기
    participant A as 알고리즘
    participant S as Stats
    participant V as 검증
    participant P as plot.py

    M->>G: 입력 패턴 생성
    G-->>M: random / sorted / reverse / duplicates
    M->>A: 작업 배열 복사 후 알고리즘 실행
    A->>S: 비교·이동·시간 기록
    S-->>M: 통계 수집 완료
    M->>V: 결과 배열 검증
    V-->>M: 정렬 여부 확인
    M->>P: CSV 파일 전달
    P-->>M: SVG 그래프 생성
```

### 5.2 시각화 자료

그래프는 입력 형태와 입력 크기에 따라 알고리즘의 차이를 서술적으로 보여준다.

#### 5.2.1 이론적 복잡도

![복잡도 개념 그래프](complexity.svg)

복잡도 그래프는 각 알고리즘이 입력 크기 증가에 따라 얼마나 빠르게 비용이 증가하는지를 보여 준다. 셸 정렬과 카운팅 정렬, 칵테일 셰이커 정렬은 같은 `n`에 대해서도 각각 다른 기울기를 보이며, 실제 측정 결과를 이해하는 기준이 된다.

#### 5.2.2 입력 형태에 따른 실행 시간

![입력 형태별 실행 시간](input-time.svg)

이 그래프는 입력 형식이 얼마나 큰 영향을 주는지를 보여 준다. 정렬된 배열은 거의 비용이 낮은 반면, 역순 또는 무작위 배열은 비용이 크게 증가할 수 있다.

#### 5.2.3 입력 형태에 따른 비교 횟수

![입력 형태별 비교 횟수](input-comparisons.svg)

비교 횟수는 각 알고리즘의 핵심 비용을 보여 준다. 예를 들어 버블 계열은 비교가 반복적으로 일어나므로, 입력이 불리한 경우 비교 횟수가 급증한다.

#### 5.2.4 입력 형태에 따른 이동 횟수

![입력 형태별 이동 횟수](input-moves.svg)

이동 횟수는 교환이 얼마나 자주 일어나는지를 보여 준다. 정렬이 중복하거나 역순인 경우, 교환이 반복되며 이동 횟수가 큰 폭으로 증가한다.

#### 5.2.5 입력 크기 증가에 따른 시간 변화

![입력 크기별 실행 시간](scale-time.svg)

이 그래프는 입력 크기가 커질수록 알고리즘이 얼마나 급격히 느려지는지를 보여 준다. 여기에서 가장 중요한 것은 “복잡도가 비슷해 보일 때도 실제 실행 시간은 입력 유형과 구현 세부사항에 따라 다르게 나타난다”는 점이다.

## 6. 결과 해석

### 6.1 알고리즘별 요약

| 알고리즘 | 최선 | 평균 | 최악 | 추가 공간 | 안정성 |
| --- | --- | --- | --- | --- | --- |
| 셸 정렬 | `O(n log n)` | `O(n^1.5)` 근사 | `O(n²)` | `O(1)` | 아니오 |
| 카운팅 정렬 | `O(n+k)` | `O(n+k)` | `O(n+k)` | `O(n+k)` | 예 |
| 칵테일 셰이커 | `O(n)` | `O(n²)` | `O(n²)` | `O(1)` | 대체로 예 |

### 6.2 실험 결과 해석

- 셸 정렬은 “큰 gap으로 빠르게 정리하고 점점 미세하게 보정하는” 방식이므로 무작위 입력에서 비교적 안정적인 성능을 보인다.
- 카운팅 정렬은 값 범위가 작을 때 매우 강력하지만, 값 범위가 커지면 메모리 사용량과 비용이 급증한다.
- 칵테일 셰이커 정렬은 구현이 간단하고, 특정 입력 형태에서는 어느 정도 효율적이지만, 전체적으로는 `O(n²)` 구조를 벗어나기 어렵다.

따라서 정렬 알고리즘을 선택할 때는 “한 번에 가장 빠른 알고리즘”을 고르기보다, 입력 데이터의 범위와 분포를 함께 고려해야 한다는 점이 핵심이다.

## 7. 결론

이번 보고서에서는 세 가지 정렬 알고리즘의 원리, 구현, 실험 절차, 시각화 결과를 함께 정리하였다. 핵심 결론은 단순히 속도 하나만 비교하는 것이 아니라, 입력 형태, 데이터 범위, 메모리 사용량, 안정성, 구현 구조를 함께 보아야 한다는 것이다.

- 셸 정렬은 간단하지만 유연한 구조로, 비교적 대규모의 무작위 배열에 적합하다.
- 카운팅 정렬은 제한된 범위의 정수 입력에서는 탁월한 성능을 낸다.
- 칵테일 셰이커 정렬은 구현이 단순하고 직관적이지만, 전체적으로는 대규모 입력에서 불리하다.

정렬 알고리즘은 어떤 문제를 풀고 있는지, 입력 데이터의 특성이 무엇인지에 따라 최적의 선택이 달라진다. 따라서 이 보고서는 단순한 비교 결과 요약이 아니라, 알고리즘을 이해하고 설계하는 데 필요한 시각을 제공하는 데 목적이 있다.
